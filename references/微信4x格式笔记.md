# 微信 4.x（Windows）本地数据格式笔记

实测环境：Weixin 4.1.13.12 x64，数据目录 `xwechat_files/<wxid>_xxxx/`。

> 本文里的 wxid、表名、消息条数、日期等**全部是脱敏值或占位符**，不是任何真实账号的数据。

## 1. 数据库

- 全部是 **SQLCipher 4**：AES-256-CBC，`page_size=4096`，`reserve=80`，每个库**独立密钥**。
- `~/.wechat-cli/all_keys.json` 里的 `enc_key` 是**裸密钥**，直接当 AES-256 key 用，
  **不要再做 PBKDF2**（这是 4.x 和 3.x 最大的差别）。
- 解密后还要回放 `-wal`（尾页还没落盘的消息在里面），`wechat_cli.core.crypto.decrypt_wal` 已实现。
- 需要解密的库（相对 `db_storage`）：

```
contact\contact.db          联系人；contact 表有 username/alias/nick_name/remark
message\message_0.db        消息分片（新）
message\message_1.db        消息分片（旧）
message\media_0.db          VoiceInfo（语音 BLOB）、Name2Id（chat_name_id 映射）
message\message_resource.db 图片/资源（本轮未用）
emoticon\emoticon.db        kStoreEmoticonFilesTable（商店包的 offset/size）
```

### 会话表与分片（最容易踩的坑）

- 会话表名 = `Msg_<md5(对方username)>`（就是对方 username 的 32 位十六进制 MD5，实测对得上）。
- **同一张表可能同时存在于 `message_0.db` 和 `message_1.db`**：老消息留在旧库，
  新消息写进新库。实测某会话绝大多数历史在 `message_1.db`，而最新几条落在
  `message_0.db`。**必须并集**，否则丢消息。
- 列语义：`create_time` 是**秒**；`local_type = (子类型 << 32) | 基础类型`，
  取基础类型要 `& 0xFFFFFFFF`；`sort_seq` 通常是 `create_time*1000`。
- `message_content` 在 `WCDB_CT_message_content == 4` 时是 **zstd 压缩**的。

### real_sender_id 必须逐库解析

`real_sender_id` 是**该库自己** `Name2Id` 表的 rowid：

| 库 | rowid | user_name |
| --- | --- | --- |
| message_1.db | 1 | 本机账号 wxid |
| message_1.db | 2 | 对方 wxid |
| message_0.db | 3 | 本机账号 wxid |

同一个「我」在 message_0 里是 3、在 message_1 里是 1 —— 硬编码 `1=我 / 2=对方` 会串人。
`media_0.db.Name2Id` 是**另一张表**（rowid = `VoiceInfo.chat_name_id`），别混用。

### 基础类型（local_type 低 32 位）对照

| 值 | 含义 |
| --- | --- |
| 1 | 文字 |
| 3 | 图片（`.dat` 加密，本轮未解） |
| 34 | 语音 |
| 47 | 表情包（`<emoji md5="…" productid="…"/>`） |
| 48 | 位置消息 |
| 49 | 应用消息（XML：引用 57 / 文件 6 / 链接 5 / 小程序 33,36,44 / 聊天记录 19 / 转账 2000 / 红包 2001） |
| 50 | 通话 |
| 10000 | 系统提示（撤回、邀请等） |

## 2. 语音：SILK inline BLOB

`media_0.db.VoiceInfo(chat_name_id, create_time, local_id, voice_data)`，
`voice_data` 是 BLOB，里面能找到 `\x02#!SILK_V3` 头，**从该标记开始**截取即为 SILK 流：

```python
i = bytes(blob).find(b"#!SILK_V3")
pysilk.decode(io.BytesIO(blob[i:]), out, 24000)   # → 24kHz 单声道 s16le PCM
```

再包 44 字节 WAV 头即可播放。实测数百条全部成功，无失败样本。

## 3. 表情包：AES-128-CBC，IV = Key

```
key   = md5(f"{seed}{wxid}EMOTICON").digest()[:16]     # wxid = 本机账号
plain = AES-128-CBC-decrypt(cipher, key, iv=key)       # 注意 IV 就是 key
```

- `seed` 是随机生成的 6~14 位十进制数字，**只存在于 `Weixin.exe` 内存**，不落盘。
  解法：扫 `VirtualQueryEx` + `ReadProcessMemory` 收集所有 `\d{6,14}` 候选，
  再用 oracle 验证——对候选 key，`P0 = AES-ECB-Dec(C0, key) XOR key` 应当命中图片魔数
  （PNG / GIF8 / `\xff\xd8\xff` / `wxgf` / `wxam` / RIFF+WEBP）。实测十几秒、几十万次尝试内命中。
- 明文以私有容器 `wxgf` 为主，少量 PNG / GIF / WEBP；这决定了后面必须实现 HEVC 解码。

### 素材来源（按优先级）

```
<wx_root>/cache/<YYYY-MM>/Emoticon/<2hex>/<md5>          看过的表情
<wx_root>/business/emoticon/Persist/<2hex>/<md5>         收藏的表情
<wx_root>/business/emoticon/PersistStore/<2hex>/<md5(包id)>  整包密文
```

商店包是**多张表情拼在一条 CBC 流**里的：按 `kStoreEmoticonFilesTable`
的 `package_id_ / md5_ / emoticon_offset_ / emoticon_size_` 切片，
切片后 `md5(切片) == md5_` 即为校验通过。

### wxgf 容器（HEVC）

```
magic(4)="wxgf" | ver(2) | flags(1) | width(2,BE) | height(2,BE) | Annex-B HEVC 流
```

**必须**用解复用器解：

```python
with av.open(io.BytesIO(data[offset:]), format="hevc") as ct:
    frames = [f.to_image() for f in ct.decode(video=0)]
```

用 `av.CodecContext.create("hevc","r").parse(...)` 会返回 **0 帧**（这是最大的坑）。
起始 offset 从 `\x00\x00\x01` 起始码候选里逐个试，拿头部声明的宽高校验。
单帧存 PNG；多帧转 `P` 模式自适应调色板 GIF（`disposal=2`、`duration=80`）。

## 4. 图片 .dat（未解密，待续）

容器为 V2：`07 08 'V' '2' 08 07` 头 + AES-128-ECB 段 + 明文段 + 单字节 XOR 尾巴。
密钥与表情那把不同，且**只在浏览过图片后才进内存**，所以要么先让用户在微信里点开图片，
要么接受 `[图片]` 占位。

## 5. 参考与致谢

本文的格式结论来自对本机数据的实测复现，其中有几条关键线索来自社区公开资料：

- 表情缓存「**IV 就是 Key**」以及 `seed` 派生公式的出现，最早见于社区逆向文章
  （CSDN 上 air846 的实测笔记）。本文在其基础上补了内存扫描 + oracle 交叉验证的实现。
- SQLCipher 4 的页面解密参数（page/reserve、裸密钥不做 PBKDF2）与 `Msg_` 分表规律，
  与 PyWxDump、wechat-dump-rs 等开源项目的观察一致。

如果你的微信版本高于 4.1.13.12，这些规律**可能已经变化**：复现失败时优先怀疑
seed 公式与分片规则，并以自己实测为准。
